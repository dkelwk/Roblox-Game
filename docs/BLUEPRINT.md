# RAID AREA 51 — Implementation Blueprint

Version 1.1 · Phase 0 + creative-director review · living document. Update it when a decision changes.

## 1. Ground rules

- **The repo is the source of truth.** Code, config and world generation live here and build
  into a place file with Rojo. Studio is where we play, inspect and polish, not where
  logic is authored.
- **Server authority.** Clients send intents ("recover capsule X", "buy upgrade Y"). The
  server decides every amount, result, price and state transition.
- **Data-driven content.** Aliens, rarities, regions, upgrades, prices, remotes, tags and
  world positions each live in exactly one config module. Gameplay code never hardcodes them.
- **Testable by construction.** Pure logic (state machines, economy math, validation, data
  migration) lives in modules without engine side effects so it runs under Lune in
  `tests/`. Services are thin adapters around that logic.
- **Nothing is "done" untested.** Every report states what was verified and how, and what
  still needs Studio or device testing.
- **One art direction: stylized low-poly.** Every model, environment, UI component and
  effect follows [ART_DIRECTION.md](ART_DIRECTION.md).

## 3. Runtime architecture

### Lifecycle

`ModuleLoader.boot(folder)` requires every ModuleScript in the folder, runs `Init` on all of
them (synchronous, no yielding, no cross-module calls), then `Start` on each in its own
thread. Services reference each other only in `Start` or later. Tested in
`tests/Bootstrap.spec.luau`.

### Server services

| Service | Responsibility | Owns |
|---|---|---|
| **NetworkService** *(added)* | Creates every remote from NetworkDefinitions, validates argument schemas, enforces per-player token-bucket rate limits, routes to handlers. Nothing else creates remotes. | `ReplicatedStorage.Remotes` |
| **PlayerDataService** | Session-locked load/save, schema migrations, autosave, save on leave and `BindToClose`, change events | player profiles |
| **PlotService** | Assigns a free plot on join, releases on leave, spawns the player at the plot's `SpawnPoint`, writes the owner sign | plot ↔ player map |
| **SpecimenService** | Capsule spawning from tagged spawn points per the region's `spawnMode` (hybrid model: `PerPlayer` instanced capsules now; `Shared` competitive pools reserved for future advanced regions and rejected by the validator until implemented), recover (range + availability + capacity), visible carry attachment, drop/return on death or leave | live capsules, carried state |
| **ScannerService** | One authoritative scanner state machine per plot: Idle → Loading → Scanning → Complete → Resetting → Idle. Rolls the result once, grants it once. | scanner states |
| **AlienCollectionService** *(renamed)* | Discovered species, owned specimens, chamber placement, chamber display models | collection records |
| **EconomyService** | The only code that changes credits. Pays chamber income on a tick and handles spend requests from other services. | credits |
| **UpgradeService** | Purchases: computes the next level and its price server-side, spends through EconomyService, publishes new stats | upgrade levels |
| **JetpackValidationService** | Fuel accounting and sanity limits (altitude ceiling, thrust while empty), relays thrust state for other clients' VFX | jetpack state |

`CollectionService` from the directive is renamed **AlienCollectionService**, because a
service with the same name as Roblox's built-in `CollectionService` (tags) invites bugs.
**NetworkService** is added so validation and rate limiting live in one place instead of
being re-implemented per service.

### Client controllers

UIController (screen stack, theme), MenuController (main menu and 3D backdrop camera),
HUDController (credits bottom-left, objective, carry, fuel, prompts),
ScannerPresentationController (plays the scan sequence for replicated states),
JetpackController (input → thrust, local movement, fuel prediction), VFXController (named,
pooled, quality-scaled effects), AudioController (categories, volumes), CameraController
(menu → gameplay transitions, reveal framing).

### Key flows

- **Recover:** proximity prompt on a capsule → `RequestRecoverCapsule(capsuleId)` →
  NetworkService checks the schema and rate limit → SpecimenService checks the capsule
  belongs to this player, is available, is within `GameConfig.Specimen.RecoverRange`, and
  carry capacity is free (`extraction_rig` stat) → the capsule attaches to the character
  (server-owned weld) → `PlayerDataChanged`.
- **Deposit and scan:** at their own scanner → `RequestDepositCapsule()` → server checks
  plot ownership, range and an Idle scanner → Loading. On entering Scanning the server rolls
  the alien once and records the specimen (unique id) and any discovery bonus in a single
  data write, then tells the client the result for presentation.
- **First discovery guarantee:** while `onboarding.firstDiscoveryGranted` is false, the roll
  returns `Onboarding.FirstSpecimenAlienId` (Glorp) instead of using the odds. The flag is set
  in the **same** data write that stores the specimen, so the guarantee is used exactly
  once, survives rejoin, and is not consumed by a scan that fails before its result is
  committed. Later scans use `RegionDefinitions` odds. Complete holds until
  `RequestContinueDiscovery()` or `CompleteTimeoutSeconds`, then Resetting → Idle. Duplicate
  starts, early continues and repeated claims are rejected by state checks.
- **Income:** every `IncomeTickSeconds`, EconomyService sums `creditsPerSecond` of the aliens
  in a player's occupied chambers (capped by `lab_capacity`) and credits that amount.
- **Purchase:** `RequestPurchaseUpgrade(upgradeId)` → the server reads the current level,
  looks up the next level's cost, and spends and levels up atomically. The client never
  sends a price or a level.

### Player data (schema v1, planned)

```lua
{
	schemaVersion = 1,
	credits = 0,
	upgrades = { jetpack_fuel = 1, lab_capacity = 1, extraction_rig = 1 },
	discovered = { [alienId] = firstDiscoveredUnixTime },
	specimens = { [specimenId] = { alienId = "glorp", obtainedAt = 0 } },
	chambers = { [slotIndex] = specimenId },
	onboarding = { firstDiscoveryGranted = false, completedSteps = {} },
	stats = { extractions = 0, scans = 0 },
}
```

Session-locked `UpdateAsync` (lock = JobId + timestamp, stale after ~30 min), retry with
backoff, autosave every `Data.AutosaveSeconds`, save on `PlayerRemoving` and in
`BindToClose`. Migrations run in order keyed by `schemaVersion`. Credits and inventory are
never written from the client.

## 4. World layout

North is −Z. Players leave their labs northward through the Extraction Gate. All numbers
come from `WorldLayout`.

```
                 z≈-1140  distant Area 51 skyline (hangars, orange-beacon tower; out of bounds)
  ┌──────────── z=-1000  north security fence, "RESTRICTED AIRSPACE" ─────────────┐
  │                                                                               │
  │                       Research Outpost (0,-770)                                │
  │                       damaged lab · depot · climbable comms tower (secret)     │
  │                                  ▲                                             │
  │  Crash Crater (-230,-540) ◄── Junction (0,-320) ──► Nest Ridge mesa (250,-520) │
  │  crashed saucer (secret on top)  signpost        ramp or jetpack to the top    │
  │  glowing crystals                ▲  truck wreck with 6 starter capsules        │
  │  x=-420                          │                                    x=420   │
  └────────────────────────┬──── z=-170 ─┴──────────┬───────────────────────────────┘
                           │   Extraction Gate (0,-150)   │
                           │  Lab 3 ▌ road ▐ Lab 6  z=-80 │
                           │  Lab 2 ▌      ▐ Lab 5  z=0   │
                           │  Lab 1 ▌      ▐ Lab 4  z=80  │
                           │  Plaza + Upgrade Station (0,140), fallback spawn
                           │  Main Facility + cyan beacon tower (0,214)
                           └──────────── z=260 ───────────┘  district x = -150..150
```

**Navigation cues.** Cyan guide lights on both road curbs point at the gate. Through the gate
the player sees the trail, the signposted junction and three distinct landmark
silhouettes. Trail markers with cyan reflectors run every 40 studs. The cyan beacon on the
Main Facility tower marks home from anywhere in the desert, while the distant skyline's
beacon is orange so the two can't be confused.

**Plots.** Six 60×60 plots face the road. Each lab has an open oversized entrance, big side
and front windows, and a skylight, so other players can see the aliens inside. Each lab
also has a scanner station, eight chamber slots (slots 1–3 are the base capacity and the
most visible), an owner sign, and its own accent color (`Palette.PlotAccents`) on the
pad, roof fascia and entrance glow so labs are recognizable at a glance. Gameplay code
uses only the `Markers` folder (`SpawnPoint`, `ScannerAnchor`) and the `Chambers` models
(`SlotIndex`, `AlienAnchor`).

**Specimen spawns.** 28 tagged points (`RA51_SpecimenSpawn`), each with `SiteId` and
`SpawnTier`:

- **Starter (6):** within 220 studs of the gate, around the truck wreck.
- **Standard (15):** spread across the three sites.
- **Elevated (4):** on top of the mesa.
- **Secret (3):** saucer dome, comms tower platform, rock spire.

Specs check that no spawn is buried in geometry, that every spawn rests on solid ground,
and that spawns are at least 6 studs apart.

**Streaming.** `StreamingEnabled` is on. Plots stream atomically. Landmarks (Main Facility,
Extraction Gate, saucer, comms tower, mesa, skyline) are persistent so the player can always
navigate by them.

## 5. Phase 1 — "First Extraction"

**Gate:** Phase 1 starts once the build runs in Studio ([STUDIO_VERIFICATION.md](STUDIO_VERIFICATION.md)
§ 1–2 pass and § 3–7 show no blocking problems).

**Order** (set by the creative director). Each step is implemented, specced, and verified
in a Studio playtest before the next one starts:

1. **Reliable player spawning.** Characters appear at their lab's `SpawnPoint` facing the
   gate, on join and on every respawn.
2. **Lab assignment.** PlotService assigns a free plot on join, releases it on leave, and
   writes the owner sign. Max players never exceeds the number of plots.
3. **Server-authoritative specimen spawning.** SpecimenService spawns `PerPlayer` capsules
   at tagged spawn points (starter tier first). Each player only sees their own.
4. **Specimen pickup.** A ProximityPrompt sends `RequestRecoverCapsule`. NetworkService
   enforces the schema and rate limit; the server checks ownership, range and capacity.
5. **Visible carrying.** The capsule is welded to the character server-side, visible to
   everyone, and doesn't hamper movement. It drops or returns on death and leave.
6. **Basic deposit.** `RequestDepositCapsule` at your own scanner (range + ownership): the
   capsule hovers at `ScannerAnchor`. The scan sequence itself is Phase 3.
7. **Validation and persistence foundations.** The NetworkService validation layer is
   complete, and PlayerDataService has schema v1, session locking, autosave, leave and
   shutdown saves, and migrations. Tested in a separate data-test experience.

**Exit criteria:**

- All specs pass.
- A two-player "Start Server" test: both players spawn at their own labs, recover, carry and
  deposit their own capsules, and neither can touch the other's.
- Data survives rejoin.
- Plaza-to-first-capsule time is measured.

**After Phase 1:**

- **Phase 2:** jetpack.
- **Phase 3:** scanner state machine, discovery with the persisted Glorp guarantee, and
  collection/chambers.
- **Phase 4:** economy, upgrades and persistence hardening.
- **Phase 5:** low-poly Blender replacements, per [BLOCKOUT_AUDIT.md](BLOCKOUT_AUDIT.md).
- **Phase 6:** UI and onboarding.
- **Phase 7:** device testing.

## 7. Blender asset workflow

**Tools:** Blender 4.2+ (tested with 5.2.2 headless) or the `bpy` wheel. All modeling is
scripted in `blender/scripts/build_<Asset>.py` on top of `ra51_pipeline.py`.

**Conventions** (enforced by the pipeline):

- 1 Blender unit = 1 stud. Z up, front faces −Y. FBX export converts to Roblox Y-up/−Z
  forward.
- Origins: bottom-center for grounded props, geometric center for carried or floating
  items.
- One mesh object per Roblox material + palette color, named
  `<Part>__<RobloxMaterial>__<PaletteToken>`. Roblox colors MeshParts from `Palette.luau` at
  bind time, so stylized assets need no textures and can't drift from the palette. Colors
  are read straight from `Palette.luau`.
- **Stylized low-poly rules** ([ART_DIRECTION.md](ART_DIRECTION.md)):
  - radial density from `radial_segments(radius)`;
  - one-segment chamfers;
  - flat shading for hard surfaces, smooth for organic forms;
  - no subdivision.
- **Triangle ceilings:** hero 4000, creature 2000, prop 800, scatter 250. Exceeding one fails
  the build.
- In Studio, `ServerStorage.Tooling.AssetBinder` applies material and palette color to
  imported meshes from their names.

**Per-asset process:**

1. Brief and in-game blockout stand-in.
2. Asset script.
3. Budget check.
4. FBX export plus `.blend` source.
5. FBX round-trip verification (names and dimensions).
6. Studio preview render to `docs/previews`.
7. Creative-director approval.
8. Studio import via the 3D Importer (Scale Unit = Stud; CollisionFidelity Box or Hull;
   check pivot, scale and orientation against the blockout).
9. In-engine screenshot.
10. Swap the blockout for the asset.
11. Update `docs/ASSET_MANIFEST.md`.

The pilot asset (Specimen Capsule v0.2, low-poly, 488 triangles) has completed steps 1–6.

**Collision:** separate simple collision parts or Box/Hull fidelity; never PreciseConvexDecomposition on
scatter. **LOD:** rely on Roblox automatic mesh LOD (RenderFidelity Automatic). Validate
with the Studio MicroProfiler on a phone before raising budgets.

## 8. VFX workflow

- `VFXController` plays **named effects** defined in `VFXDefinitions`: `ScannerActivate`,
  `ScanRing`, `DiscoveryReveal[tier]`, `JetpackIgnite`, `JetpackTrail`, `JetpackBoost`,
  `JetpackLand`, `CollectBurst`, `CreditsPop`, `UpgradeFlash` and `ChamberActivate`.
- Each effect returns a cleanup handle. Emitters are pooled, not created per play.
  Gameplay code never builds particles inline.
- **Quality tiers** (Low/Medium/High) come from a settings toggle and the device's
  graphics quality level. Tiers scale emitter rates, beam counts and light usage. Budgets:
  ≤ 6 active emitters per effect, no full-screen flashes, lights only on hero moments.
- Rarity drives reveal intensity (`RarityDefinitions.revealTier`). Rare and epic reveals
  get more, not longer: the whole reveal stays under ~2.5 s, and the player can always
  continue.
- Blender produces effect meshes (scan ring, energy shells) and rendered flipbook sprite
  sheets, uploaded as assets and referenced from `VFXDefinitions`.

## 9. UI workflow

- **Native Roblox UI built from Luau component functions** themed by `UITheme`:
  `Palette.UI`, a spacing scale, a type scale (Builder Sans), corner radius, stroke and
  shadow styles. No ad-hoc colors or sizes.
- **Responsive by default:**
  - `ScreenGui.ScreenInsets = CoreUISafeInsets` for safe areas.
  - Anchor-based layouts with `UIScale` driven by viewport size.
  - Touch targets of at least 44 px.
  - Nothing important under the mobile jump/thrust buttons.
- **Screens:**
  - Main menu over a scripted 3D lab camera.
  - HUD: credits bottom-left with an animated count; objective; carry; fuel when relevant;
    contextual prompts.
  - Scanner reveal.
  - Collection: cards with `ViewportFrame` previews, rarity treatment, and an undiscovered
    state.
  - Upgrades.
  - Settings: VFX quality, music and SFX volume.
- GUI objects are never named `Name` or `Size` (enforced for world signage by a spec;
  the UI specs will extend this).
- **Device matrix in the Studio emulator:** 1920×1080, 1280×720, iPhone SE (667×375),
  notched phone (~852×393), tablet 1024×768. Then a real phone through a test place.

## 10. Test strategy

| Layer | Tool | What it proves |
|---|---|---|
| Static | StyLua, Selene (game, specs, scripts), luau-lsp strict with Roblox types and a Rojo sourcemap | formatting, lint, type safety of all game code |
| Unit/integration | Lune specs against the built place (`scripts/test`) | config correctness and pacing, validator catches each class of mistake, boot lifecycle, world invariants (anchors, spawns, routes, orientation, palette, budgets, determinism), Studio tooling |
| Harness parity | `tests/Harness.spec.luau` | Lune's Roblox math matches the engine. Lune 0.10.5's `CFrame.lookAt` mirrors the Z axis; the runtime corrects it, and these specs plus the orientation specs fail if that regresses. |
| Visual | Blender preview renders (`tools/preview`, asset previews) | layout, silhouettes, palette, readability (not Roblox lighting) |
| Engine | Studio Play / Start Server (2+ players) with a per-milestone checklist | physics, replication, prompts, streaming, UI rendering |
| Data | Separate published test experience with API access | session locking, rejoin persistence, shutdown saves |
| Device | Studio emulator + real phone | layout, touch, performance (MicroProfiler) |

`lune run scripts/check` runs every automated layer. Each new pure-logic module gets
specs. Each service gets a Studio checklist in its PR.

## 11. Environments and reboot safety

- The existing game place is **not touched**. The reboot never publishes to it.
- **Development place:** open `build/RaidArea51.rbxl` → *File → Publish to Roblox As…* →
  create a **new** experience (suggested name "RAID AREA 51 [DEV]"). Use `rojo serve` for live
  sync into it. Full Mac steps, including the Claude Code + Studio MCP connection, are in
  [STUDIO_SETUP.md](STUDIO_SETUP.md).
- **MCP safety:** MCP clients can read and modify any open place. Only the dev place is open
  while Claude is connected.
- **Data testing:** a second private experience with *Enable Studio Access to API
  Services* on, so DataStore tests never touch production keys. Store names are versioned
  (`GameConfig.Data.StoreName`).
- Work happens on feature branches with PRs. Nothing reaches the live game without explicit
  sign-off.
